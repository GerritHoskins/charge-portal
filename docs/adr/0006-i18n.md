# ADR 0006: Internationalisation (de, en)

**Status:** accepted (demo)

## Context

The UI was hard-coded German. White-label customers and an international team need English, and hard-coded strings
make that a later, larger migration than doing it while the page count is small.

## Decision

1. **`@nuxtjs/i18n`, locales `de` (default) and `en`, no URL prefix.** `/portal/...` paths are shared with legacy and
   with the rollout inventory; a `/en/...` prefix would multiply every route. The language comes from a cookie, the
   browser language, or the switcher in the header; German is the fallback.
2. **Messages live in `i18n/locales/{de,en}.json`**, keyed by page (`stations.col.name`). Pages never contain visible
   strings. Status and reason labels are looked up by their contract value (`stations.status.faulted`), so a new enum
   value without a translation is visible in review.
3. **Design-system components stay translation-free.** They take text as props or slots, with a German default only for
   Storybook (`DsStatusBadge` label, `DsTextField` `requiredText` / `errorPrefix`). Components must not call
   `useI18n`; ESLint forbids it in `app/components/ds/`.
4. **Formatting follows the locale, the time zone does not.** `useFormatters` uses `de-DE` / `en-GB` for dates, numbers
   and EUR but always `Europe/Berlin`, so server and client render identical text (no hydration mismatch).
5. **`<html lang>` follows the active locale** (WCAG 3.1.1); an E2E test checks the switch and runs axe on the English page.
6. **E2E tests pin `de-DE`** (Playwright `use.locale`), so existing German assertions stay valid, and one test proves an
   English browser gets English.

## User and business value

White-label tenants can be onboarded in English-speaking markets without a fork, and screen readers pronounce the page
correctly because the language attribute is right.

## Consequences

- **Dispute validation messages are still German**: they originate in legacy (`422` body) and are shown as received.
  Translating them needs error codes in the contract and is not done.
- Drift between the catalogues is caught by `tests/unit/i18n-catalogues.test.ts` (same keys, same placeholders, no empty values, every statically referenced key exists). Keys built dynamically (`stations.status.${status}`) are not covered by the last check.
- The bundle grows by the message catalogues and the i18n runtime; `npm run budget` keeps that honest.
- Pluralisation is minimal ("5 stations shown" is not pluralised); fine for the demo, not for production copy.
